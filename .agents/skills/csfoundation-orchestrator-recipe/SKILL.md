# csfoundation Orchestrator Recipe Management

## Overview

This skill guides the agent in inspecting, auditing consistency, updating, and maintaining the **csfoundation** build recipe. `csfoundation` uses the `csorchestrator` framework to define cross-platform base-libraries build pipelines in Python and generate corresponding GitHub Actions CI workflows.

## Dependencies

- **Python**: `>= 3.11` in active `.venv`
- **csorchestrator**: Available as an editable package in the local environment
- **Tools**: `pre-commit`, `ruff`, `mypy`, `pytest`

## Quick Start

To audit recipe consistency and re-generate the GitHub Actions CI workflow:

```bash
# 1. Re-generate GitHub Actions workflow from csfoundation_project.py
./csfoundation_project.py generate-github-workflow

# 2. Run quality checks and ensure git hygiene
pre-commit run --all-files
```

## Workflow

Follow these steps when interacting with or modifying the `csfoundation` build recipe:

### 1. Recipe & Consistency Audit
Inspect the core configuration files before making changes or upon request:
- [`csfoundation_project.py`](file:///home/sceriani/myWorkspace/csfoundation/csfoundation_project.py): Core pipeline definition, repository list, and precompiled-library downloads.
- [`pyproject.toml`](file:///home/sceriani/myWorkspace/csfoundation/pyproject.toml): Project metadata and versioning.
- [`csfoundation/csorchestrator_config.py`](file:///home/sceriani/myWorkspace/csfoundation/csfoundation/csorchestrator_config.py): Project identity constants (single source of truth for name/version) and Linux system requirements installation.
- [`tests/`](file:///home/sceriani/myWorkspace/csfoundation/tests): Recipe tests (`test_csorchestrator_config.py`: first-party/managed dependency resolution) plus placeholder tests.

**Verification Checklist (Strict Fail-Loud Policy):**
- **Extra Files**: Check every path passed to `additional_files_list` in `create_default_orchestrator()` (e.g. `Path("csfoundation/csorchestrator_config.py")`). Verify that every referenced file exists on disk.
- **Version Alignment**: Verify that `CSFOUNDATION_PROJECT_VERSION` in `csfoundation/csorchestrator_config.py` (e.g. `0.1.0`) aligns with `version` in `pyproject.toml` and artifact package names (`csfoundation-<version>-...`).
- **Repository List**: Verify that every repository in `repos` is a known csorchestrator-supported repo and that its `BuildConfig` (`DEBUG_RELEASE_RELWITHDEBINFO_PARANOID`, or `None` for checkout-only repos like `csCMake`) matches the repository's intended configuration.
- **Precompiled Libraries**: The "Get Precompiled Libraries" phase goes through `install_csfoundation_build_dependencies()` (internal, used by `csfoundation_project.py`) in `csfoundation/csorchestrator_config.py`, which resolves the `third_party_base_libs` subset via `resolve_required_third_party_libraries()` and the `csqt6` subset via `resolve_required_qt6_libraries()` — one map per providing release (`THIRD_PARTY_LIBRARY_DEPENDENCIES` / `QT6_LIBRARY_DEPENDENCIES`, composed over `FIRST_PARTY_LIBRARY_DEPENDENCIES`), no `if lib == "qt6"` filtering — and delegates to the `third_party_base_libs` (release `v0.1.0`) and `csqt6` (release `v6.11.1`) helpers (`qt6_mapping_function` param, default `qt6_mapping`). The customer-facing `auto_install_csorchestrator_managed_libraries()` calls the internal helper and additionally downloads the requested prebuilt first-party libs from the `csfoundation` release itself (`CSFOUNDATION_RELEASE_TAG`). If a release (e.g. `csqt6`) is not published yet, `generate-github-workflow` cannot complete its download steps: document any temporary workaround explicitly in the run log / commit message and restore the recipe afterwards — never hide temporary state.
- **SDK Vendoring**: `csorchestratorsdk/portable/` is autogenerated from `csorchestrator`; do not edit manually. If it needs updating, re-export it by running `./csfoundation_project.py generate-github-workflow`.

> [!IMPORTANT]
> If any consistency check fails (missing extra file, mismatched version, unknown repository), **fail loudly**. Report the exact discrepancies to the user for guidance rather than silently continuing or guessing.
### 2. Local Execution Policy (Build Guard)
- **DO NOT run full local builds of the base libraries** (e.g., executing all phases of `./csfoundation_project.py` locally). Building every library on the full matrix requires significant time, disk space, and RAM.
- Only run unit tests (`pytest`) or dry-run validation when checking local configuration logic.

### 3. CI Workflow Re-generation
Whenever `csfoundation_project.py`, the repository list, or execution phases are modified, re-generate the GitHub Actions workflow:

```bash
./csfoundation_project.py generate-github-workflow
```

- Verify that [`.github/workflows/csfoundation.yml`](file:///home/sceriani/myWorkspace/csfoundation/.github/workflows/csfoundation.yml) has been updated with the modified phases and matrix.
- Inspect the git diff using `git diff .github/workflows/csfoundation.yml` to ensure changes match expectations.
- Note: running the generator executes the "Get Precompiled Libraries" downloads (manifest + bundle), so it requires the corresponding GitHub releases to exist.

### 4. Code Quality & Pre-commit Verification
Before concluding any changes, run the repository's validation hooks:

```bash
pre-commit run --all-files
```

If hooks report formatting errors or auto-fix lines:
1. Review the modified files.
2. Re-run `pre-commit run --all-files` to ensure all checks pass cleanly (`Passed`).

### 5. Documentation Synchronization
If recipe arguments, version, or repository configurations were updated:
- Update [`README.md`](file:///home/sceriani/myWorkspace/csfoundation/README.md) to keep the included-libraries table, build matrix, and command instructions accurate.

## Common Mistakes

1. **Attempting a full local build**: Running `./csfoundation_project.py` without understanding that it will attempt to download and build all base libraries. Full builds are meant for CI runners or dedicated build machines.
2. **Forgetting to re-generate the workflow**: Modifying `csfoundation_project.py` without running `./csfoundation_project.py generate-github-workflow`, leaving `.github/workflows/csfoundation.yml` out of sync with the Python recipe.
3. **Missing extra files in release**: Adding a file to `additional_files_list` in `csfoundation_project.py` that does not exist or has a typo in its relative path, causing release packaging jobs to fail in CI.
4. **Version mismatch**: Updating `CSFOUNDATION_PROJECT_VERSION` in `csfoundation/csorchestrator_config.py` without updating `pyproject.toml` or the artifact names (`csfoundation-<version>-...`).
